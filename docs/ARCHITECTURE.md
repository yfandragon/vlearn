# 这个项目到底是怎么回事

> 写给「完全不懂这些技术」的人。读完你应该能回答四个问题：
> 它用了什么、怎么串起来的、为什么这么做、我该从哪里开始改。

---

## 零、先用一个比喻

想象你请了一个助理帮你整理一小时的视频：

1. **先去拿稿子**——能找到现成字幕最好，找不到就自己听写（这一小时音频，助理听了 10 分钟）
2. **把稿子切成几段**——太长了一次看不完
3. **每段写要点**，标上「这段在第几分钟」
4. **最后合并成一份完整笔记**

`vlearn` 就是这个助理，只不过「听写」和「写要点」分别交给两个专门的程序。
你要做的只有一件事：**把视频链接递给它**。

## 一、术语表（每个词一句话）

| 词 | 说人话 | 在这个项目里 |
|---|---|---|
| **CLI** | 命令行界面，敲命令而不是点按钮 | `python3 vlearn.py ...` 就是 CLI |
| **URL / 链接** | 网页地址 | 你粘进去的那串 `https://...` |
| **字幕文件** | 视频自带的文字稿，带时间码 | 优先用它，因为它几乎零成本 |
| **VTT / SRT** | 字幕的两种文件格式 | 内容长这样：`00:00:12.500 --> 00:00:15.000 大家好` |
| **ASR** | Automatic Speech Recognition，语音转文字 | 没字幕时用它「听写」 |
| **Whisper** | OpenAI 开源的语音识别模型 | `faster-whisper` 是它的加速实现 |
| **模型（model）** | 一个几百 MB 的「大脑文件」 | tiny/base/small/medium/large，越大越准越慢 |
| **LLM** | 大语言模型，比如 DeepSeek、GPT | 负责「读稿子写笔记」 |
| **token** | 模型计费的最小单位，约等于 1~2 个汉字 | 你的额度就是按它算的 |
| **API** | 程序之间说话的接口 | 有时我们用 API 直接拿 B 站数据 |
| **额度** | 你订阅里包含的调用次数 | opencode Go 的订阅，不是另付钱 |
| **缓存** | 把算过的结果存下来，下次直接拿 | 重跑同一视频不再消耗额度 |
| **SSE** | 服务器持续往浏览器推消息的技术 | 网页界面里那条实时滚动的日志 |
| **Git** | 版本管理工具，记录每次改动 | 你的项目已经 git 初始化过了 |
| **GitHub** | 存放 Git 仓库的网站 | 你准备发布的地方 |

## 二、整体架构：五个阶段

```
                        ┌──────────────────────────────────────┐
   你输入               │  阶段 1：拿到文字                     │
   ──────►              │                                      │
   YouTube 链接 ────────►│  yt-dlp 抓字幕 ──┐                   │
   B 站 BV 号  ────────►│  B 站 API 拿字幕 ─┤ 有字幕？ ──是──► │──┐
   本地 mp4    ────────►│                  │                   │  │
                        │                  └─否─► 语音识别 ─────│──┤
                        └──────────────────────────────────────┘  │
                                                                   ▼
                        ┌──────────────────────────────────────┐
                        │  阶段 2：清洗成「段落」               │
                        │  字幕 → 去重 → 合并 → 每段带时间戳    │
                        └──────────────────────────────────────┘
                                                                   │
                                                                   ▼
                        ┌──────────────────────────────────────┐
                        │  阶段 3：按字数切块                   │
                        │  ≤12000 字 → 1 块；更多 → 多块         │
                        └──────────────────────────────────────┘
                                                                   │
                                                                   ▼
                        ┌──────────────────────────────────────┐
                        │  阶段 4：让 LLM 写要点                 │
                        │  opencode run -m opencode-go/...     │
                        │  （用的是你的订阅额度）                │
                        └──────────────────────────────────────┘
                                                                   │
                                                                   ▼
                        ┌──────────────────────────────────────┐
                        │  阶段 5：落盘                         │
                        │  notes.md / transcript.md / meta.json│
                        └──────────────────────────────────────┘
```

**关键点**：阶段 1 有三条路（YouTube / B 站 / 本地），但它们最后都汇成同一种数据结构——
**一组「（开始时间, 结束时间, 文字）」的三元组**。后面的阶段完全不关心这些文字是从哪来的。

这种「中间统一成一种格式」的做法，是软件里最常见的解耦手段。你以后看到 `cues` 这个词，
指的就是这个三元组列表。

## 三、每一步在干嘛（对应真实代码）

### 阶段 1：拿到文字

`vlearn.py:1036` 的 `prepare()` 是总调度：

- 本地文件 → 直接 `transcribe()`（`vlearn.py:889`）
- B 站 → `bili_prepare()`（`vlearn.py:322`）走 API；失败则回退 yt-dlp
- 其他 → `fetch_meta()`（`vlearn.py:144`）用 yt-dlp 拿元数据，然后 `pick_subtitle()` 挑字幕

**为什么 B 站要单独写一套？**
B 站的网页端有风控，yt-dlp 直接访问会返回 `412 Precondition Failed`。但它的开放 API 是通的，
所以元数据和音轨改走 API。这是「产品特性逼出来的架构分支」，不是设计上的洁癖。

**YouTube 为什么要「换客户端」？**
YouTube 一直加反爬。默认的 web 客户端经常被拦（报 `The page needs to be reloaded`），
但 `android` 客户端还能用。所以 `fetch_meta()` 会依次试 `default → android → tv → web_safari`，
哪个能拿到字幕就用哪个。

### 阶段 2：清洗成段落

字幕文件不是给人读的，它有很多毛病：

```
00:00:00.12 --> 00:00:02.40   大家好，今天我们
00:00:02.40 --> 00:00:04.80   大家好，今天我们
00:00:02.40 --> 00:00:04.80   大家好，今天我们聊视频工具
```

同一句话会重复三遍（这是滚动字幕）。`parse_vtt()`（`vlearn.py:369`）负责拆开，
`dedupe_cues()`（`vlearn.py:408`）负责去重，`to_paragraphs()`（`vlearn.py:424`）把
碎句子合并成能读的段落，每段记下开始时间。

**为什么一定要保留时间戳？**
因为这个工具的核心价值是「可回查」。没有时间戳，LLM 很容易编造内容，你也没法核对。
时间戳是约束，也是质量保证。

### 阶段 3：切块

`to_blocks()`（`vlearn.py:444`）按字数切。为什么？因为模型一次能读的字数有限，
而且一次读太多，中间部分容易被忽略（这是 LLM 的通病，叫「lost in the middle」）。

### 阶段 4：调模型

这里是整个项目最「脏」的部分，因为要复用别人的 CLI，而不是干净的 API。

```python
opencode run --format json --standalone --auto -m opencode-go/deepseek-v4.1-flash "提示词"
```

代码在 `call_model()`（`vlearn.py:610`）。要处理三件事：

1. **参数不一样**：opencode 1.x 和 2.x 的 flag 不同，所以 `opencode_caps()`（`vlearn.py:513`）
   先跑一次 `--help`，看它支持什么，再拼命令。
2. **输出不是纯文本**：它吐的是 JSON 事件流，`scan_stream()`（`vlearn.py:462`）从中把正文抠出来。
3. **会失败**：额度过期、限流、超时，`explain_failure()`（`vlearn.py:597`）负责翻译成
   人能看懂的修复步骤。

**为什么要这么麻烦？**
因为这样不花钱。走 API 要绑卡、按 token 计费；走订阅额度，边际成本是 0。
代价就是上面这些麻烦。这是一次明确的取舍。

### 阶段 5：落盘

```
out/<视频id>/
├── notes.md        ← 给人看的成品
├── transcript.md   ← 给机器/检索用的原文
├── meta.json       ← 溯源信息（谁、多长、用的什么模型）
└── chunks/         ← 中间结果，也是缓存
```

## 四、五个关键设计决定（以及为什么）

### 1. 字幕优先，ASR 兜底

下字幕是秒级，跑 Whisper 是分钟级 + 几百 MB 模型。**大多数视频都有字幕，所以把快的路放前面。**

### 2. 单文件，不拆包

`vlearn.py` 有 1300 行，全在一个文件里。这看起来「不专业」，但好处是：
`curl -O` 下来就能跑、`pipx install` 不用管包结构、你打开就能搜到任何函数。
**这个项目的规模（一个人维护、十几个功能）还没到需要拆包的程度。**

### 3. 复用 CLI 额度，而不是 API

见上一节。牺牲了「干净」，换来了「免费」。

### 4. 缓存键 = 后端 + 模型 + 内容

一开始只用了内容做键，结果换模型后仍拿到旧笔记。现在把模型也编进键里。
**这类 bug 的特点是：不报错，只是悄悄给你错的东西。** 所以测试里专门有 `cache_key` 的用例。

### 5. 网页界面只是壳

`webui.py` 里没有一行业务逻辑，它只是：
启一个 HTTP 服务 → 收到请求 → `subprocess.Popen(["python", "vlearn.py", ...])`
→ 把子进程的输出用 SSE 推给浏览器。

**这意味着：命令行能跑通的，界面一定能跑通；界面出问题，回命令行用同样的参数跑一遍就能定位。**
如果界面自己实现了一套逻辑，就会变成两个 bug 来源。

## 五、一次运行的真实时间线

以 18 分钟的视频为例（真实日志）：

| 时间 | 发生了什么 | 谁在干 |
|---|---|---|
| 0s | 读元数据（标题、时长、有哪些字幕） | yt-dlp |
| 2s | 默认客户端被拦，换 android 客户端 | `fetch_meta()` 的重试 |
| 5s | 下载中文字幕（VTT） | `download_subtitle()` |
| 5.5s | 290 条字幕 → 26 个段落 | `parse_vtt` + `to_paragraphs` |
| 6s | 5,392 字 < 12,000，判定「1 次成稿」 | `to_blocks` |
| 7s | 发请求给 DeepSeek（含 5,625 字转写） | `call_model` |
| 40s | 模型返回结构化 Markdown | 网络 + 推理耗时 |
| 43s | 写入 4 个文件 | `run_summarize` |

总共 1 次模型调用。如果视频 1 小时，大约 3 次（2 块 + 1 合并）。

## 六、数据与隐私

- **视频和音频**：只在本机下载，存在 `out/_audio/`，不传给除了模型以外任何地方
- **转写文本**：会作为 prompt 发给模型供应商（这是必须的，它要读才能总结）
- **登录态**：cookie 只在内存里用于请求 B 站，不落盘
- **模型供应商能看到什么**：你视频的文字内容。如果内容敏感，用 `--asr none` 只抓字幕，
  或者换本地模型（这是后续可以做的方向）

## 七、自己动手改（三个练习）

### 练习 1：改输出格式（最简单）

打开 `vlearn.py`，找到 `NOTE_SPEC`（约 704 行），它长这样：

```python
NOTE_SPEC = """【输出格式】
# {title}
> 一句话结论：……
## 核心要点
...
"""
```

把它改成你想要的，比如加一节「## 我的疑问」：

```python
## 我的疑问
列出视频里没讲清楚、需要我另外查的 3 个问题。
```

改完跑 `python3 -m unittest discover -s tests` 确认没弄坏，然后 `--force` 重跑。
（注意：改了 prompt 但内容没变时，缓存仍然会命中，所以要加 `--force`。）

### 练习 2：换模型

```bash
python3 vlearn.py "URL" --model opencode-go/deepseek-v4-pro
```

想永久改默认：`vlearn.py` 约 28 行的 `DEFAULT_MODEL`。

### 练习 3：加一个新的输出文件

`run_summarize()` 约 1141 行，末尾有一串 `(out_dir / "xxx.md").write_text(...)`。
照着写一个 `summary.json`，把 `blocks` 的数量、字符数存进去。这就是「加功能」的最小闭环。

## 八、技术栈清单

| 技术 | 是什么 | 为什么选它 | 替代方案 |
|---|---|---|---|
| **Python 3.9+** | 编程语言 | macOS 自带，零安装 | Node.js（要装 nvm） |
| **yt-dlp** | 视频下载器，YouTube-dl 的活跃分支 | 支持平台最多、维护最勤 | yt-dlp 是事实标准 |
| **faster-whisper** | Whisper 的 CTranslate2 实现 | 比原版快 4 倍，且 PyAV 自带解码**不用装 ffmpeg** | whisper.cpp（更快但要 ffmpeg + 手动编译模型） |
| **opencode CLI** | 终端里的 AI 编程助手 | 有 Go 订阅额度，按次不按 token 计费 | Claude Code、Codex（都用同一套思路） |
| **DeepSeek V4.1 Flash** | 国产大模型 | 中文好、便宜、Go 订阅里包含 | GPT、Qwen |
| **http.server + SSE** | Python 标准库的 HTTP 服务 | 不装 Flask，`pip install` 只有一个依赖 | FastAPI（要装 uvicorn） |
| **argparse** | 标准库的命令行解析 | 零依赖，自带 `--help` | click、typer |
| **unittest** | 标准库的测试框架 | 零依赖，CI 里直接跑 | pytest |

**一个共同点**：除了 `yt-dlp`（必需）和 `faster-whisper`（可选），其余全是 Python 标准库。
这是刻意的——依赖越少，别人 clone 下来越容易跑起来。

## 九、如果你想继续学

按这个顺序，每个都对应项目里的一段真实代码：

1. **先读 `parse_vtt` 和 `to_paragraphs`**（约 369~460 行）——最简单的纯函数，没有网络、没有模型
2. **再读 `run_summarize`**（约 1141 行）——看主干怎么把各阶段串起来
3. **然后读 `call_model` 和 `opencode_caps`**（约 513~630 行）——看怎么跟外部 CLI 打交道、怎么处理不确定性
4. **最后读 `webui.py`**——看怎么把一个 CLI 包装成网页应用

每读一段，就跑一次 `python3 -m unittest discover -s tests -v`，看测试怎么描述这段代码的行为。
**测试就是最好的文档。**
